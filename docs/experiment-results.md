# 正式实验结果

执行日期：2026-11-22（Asia/Shanghai）。所有数字由 `results/raw/` 中的真实
运行记录生成；未用最佳运行替换失败运行。

## 结论

原始 Developer→QA 方案不是一个有效方案：严格完成率只有 2/9（22.2%）。
主要失败不是前端代码错误，而是 Developer 已留下有效 diff、甚至通过外部测试后，
因 30k 子预算未能生成最终文字报告，导致 QA 根本没有启动。

artifact-first 改进将严格完成率提高到 7/9（77.8%），相对原方案增加 55.6 个
百分点；9/9 运行均通过构建、6 个公开测试和 2 个隐藏测试。它仍未超过 Single 的
8/9（88.9%），因为两次 QA 响应触发供应商输出截断，按预注册规则判为无效。

因此，本项目不声称“多智能体普遍优于单智能体”。更准确的结论是：独立 QA 能找到
Developer 未覆盖的真实回归，但可靠的 artifact 交接是收益出现的前提；在这组小型
任务上，改进方案接近但没有超过 Single 的严格完成率。

## 总体结果

| 条件 | 严格完成 | 外部验收通过 | token，均值±样本 SD | Agent 秒，均值±样本 SD |
|---|---:|---:|---:|---:|
| Single | 8/9（88.9%） | 9/9（100%） | 35,690 ± 4,674 | 26.29 ± 5.83 |
| 原始 Dev-QA | 2/9（22.2%） | 8/9（88.9%） | 26,472 ± 5,968 | 23.26 ± 14.31 |
| artifact-first Dev-QA | 7/9（77.8%） | 9/9（100%） | 29,235 ± 4,632 | 32.06 ± 8.07 |

“严格完成”同时要求工作流有效和外部验收通过；“外部验收”单独列出是为了区分
代码产物质量与编排终止问题。改进方案相对 Single 平均少用 6,455 token
（-18.1%），但慢 5.77 秒（+21.9%），且严格完成少 1 次。较少 token 部分来自
角色提前停止，不能解释为纯效率提升。

## 关键任务的三次独立重复

| 任务 | 条件 | 完成 | 平均 token | 平均 Agent 秒 |
|---|---|---:|---:|---:|
| T03 失败重试 | Single | 3/3 | 33,726 | 24.56 |
| T03 失败重试 | 原始 Dev-QA | 2/3 | 25,628 | 27.99 |
| T03 失败重试 | artifact-first | 3/3 | 28,882 | 29.55 |
| T04 响应式导航 | Single | 2/3 | 39,691 | 25.15 |
| T04 响应式导航 | 原始 Dev-QA | 0/3 | 24,007 | 12.90 |
| T04 响应式导航 | artifact-first | 2/3 | 27,282 | 28.15 |

T03 的改进方案稳定通过。T04 的一次失败不是隐藏测试失败，而是 QA 输出被供应商截断；
同一运行的 build、公开测试和 2/2 隐藏测试仍通过。这说明 artifact-first 修复了
Developer 交接，但没有消除所有下游模型/API 终止风险。

## QA 是否产生了独立价值

改进组有 7 次 Developer artifact 恢复、2 次 Repair artifact 恢复。QA 两次给出
FAIL，均有可复现的 diff 证据，并触发了针对性修复：

- T01：Developer 在没有搜索词且任务列表为空时错误显示
  `No tasks match your search.`；QA 要求仅在 active query 下显示，修复后 8 项测试通过。
- T03 r1：Developer 删除了既有 `.sync-state.error` 样式；QA 要求恢复旧错误态样式，
  Repair 修改 diff 后 8 项测试通过。

这两项不是重复 Developer 已执行的公开测试，而是对旧空状态和旧视觉状态的 diff
审查。它们支持“QA 角色有机制价值”，但 5 个受控任务不足以支持广泛泛化。

## DesignBench 外部验证

在固定的 `db-e30` 三次配对中，Single 通过 2/3，Dev-QA 通过 3/3；平均完成率差
33.3 个百分点。Dev-QA 平均多用 6,156 token、慢 11.23 秒。r2 中 QA 发现
Developer 将未要求修改的 toolbar 外边距从 `p-4` 改为 `p-2`，Repair 恢复后通过；
r3/r4 QA 均 PASS。该结果只支持一个静态前端编辑任务上的稳健性结论。

其余四题随后各补跑一次 Single 与 artifact-first Dev-QA。Single 为 4/4 有效运行、
1/4 最终通过，平均 23,303 token、13.40 秒；Dev-QA 为 3/4 有效运行、1/4 最终
通过，平均 22,071 token、20.31 秒。Dev-QA token 均值更低不是效率提升，而是
最复杂的 `db-e27` 在 Developer 部分编辑和 QA 输出截断后提前失败。简单编译题
`db-c06` 中双方完成同一行修复，Dev-QA 额外使用 3,626 token、慢 5.95 秒，没有
结果收益。这组一次重复的 pilot 说明应按任务风险自适应启用 QA，不能声称多 Agent
普遍优于 Single。

## 局限

- 只有 5 个受控功能任务、1 个三次重复的外部静态任务和 4 个一次重复 pilot，样本很小。
- 三种条件使用同一 `deepseek-flash` 服务别名，无法固定供应商权重哈希。
- QA 与 Developer 使用同一模型，错误相关性可能较高。
- 两次供应商 generation truncation 直接影响严格完成率。
- 隐藏测试覆盖功能状态，不代表完整视觉质量；DesignBench 又只有静态视觉真值。

完整机器可读统计见 `results/summary.json`、`results/designbench/summary.json` 和
`results/designbench/four-task-pilot.json`；每次
模型轨迹、diff、命令日志和评分均保存在相应 `results/raw/` 目录。
